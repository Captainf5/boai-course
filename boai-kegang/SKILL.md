# 博AI课纲

## 工作原则

- 本机双端共用同一维护源；更新本 Skill 前先读 `CROSS-PLATFORM.md`，若有 `AI-README.md` 则核对本机入口。修改源文件后重建发行包并验证，不编辑手机聚合稿或 ZIP 内副本；不要同时在两端修改同一文件。

- 当前用户明确要求优先于本 Skill，主规则优先于历史课纲。默认沿用用户认可的“中国移动在线三天课纲”的表达与视觉体系，不照抄其旧事实、工具承诺和错误时间。
- 手机与电脑同标准：完整课纲、同一当前课程基线、同一质量清单和同一排版程序；不得把手机输出降级成提纲摘要。不同模型可以措辞不同，但都必须通过同一质量门槛。
- 只修改用户要求的范围。已明确时长、岗位与主题时直接推进；确实影响方向或权限的缺失信息才询问。假设与待确认事项放在回复或内部记录，不放进客户版结尾。
- 请求仅为建议或分析时，不擅自改文档；请求修改、生成、排版时完成对应文件并核验。发布与推送需要实际授权。
- 本技能统一在课程合集 `boai-kegang/` 维护，旧仓库仅作历史来源。13份当前课程正文只在`outputs/catalog/`维护，references负责索引与规则；文件路径相对包根目录，不依赖作者电脑的 D 盘。
- Codex与WorkBuddy是写作执行工具，不代表课程必须讲它们。按实际客户、岗位和主题选内容；不要把本次WorkBuddy课程的章节、时长与工具变成所有课程的硬模板。

5. 定制与视觉交付同时参考 `references/quality-baseline-2026-09-15.md`；当前用户要求和主规则优先。`大展宏图方法论.md`：研发课程或调整教学逻辑时读取。

## 客户版表达

- 对外课纲H1固定为 `# 【博AI增效-{时长}】{课程名}`；时长写1D/2D/3D或实际小时（如2H、3.5H）。禁裸标题、旧式连字符；仅OPC用 `# 博AI增效-OPC实战工作坊`。
- **客户版不写内部沟通内容**：对接反馈、调研原声引用、定制过程说明一律不进课纲。默认用 Type B（主讲人→课程说明→大纲→…），不用 Type A；确有问卷/调研且客户要求展示时才用 Type A。痛点场景用中性表述（如"高频痛点"），不引用学员原话。
- 默认采用“模块名＋业务价值”的标题，例如“AI×公文与方案写作——从‘想清楚’到‘写出来’”。避免每章都堆叠同一种口号。
- 每个教学模块（含加餐）先单列 **关键词**，再写 **讲解要点、演示、学员练习、产出物**，有必要时列工具。关键词选最有辨识度的内容，不替代正文，不为凑数量堆术语。
- **讲解要点写法（定制课）**：第一句先锚定场景——"以XX业务线XX案例为场景，讲清XX方法"，一句话说清，不解释课程设计思路、不写"引入"“以…为主案例引入——”等冗长铺垫、不重复标题已含信息；方法论用括号或分号紧凑内嵌。通用课讲解要点用有具体场景、对象与动作的自然语句，可用分号串联相关步骤；内容过长则拆成少量子项。不得硬限“一行”“最多三组”，也不得写成抽象名词串。
- **演示写具体案例过程**：用箭头串联的真实工作链路（如"脱敏质检记录→稽核报告初稿→月度汇报→培训课件与试题→保存为模板"），不写"功能走查""效果对比"等抽象说法。
- 演示写一条看得懂的工作过程；练习明确学员做什么；产出明确数量、文件类型和可用状态。验收自然融入练习或产出，不默认追加一整排生硬字段。
- 3—5 秒短句用于课堂开场，详细节奏放讲师教案。客户课纲不能退化成口播台词、反问句列表或讲师操作日志。
- 正文保持专业、亲切、可阅读。不出现内部“大展宏图”“BOBO-123”等名称，除非用户明确要求介绍方法论本身。
- 客户版不附内部修订版本号、状态、更新时间、来源清单、净授课分钟数或模型运行说明；6X畅销版等产品后缀按已确认命名进入课程标题。
- **全文密度（硬规则）**：讲解要点、演示、学员练习三项是压缩重点，去铺垫、去重复、去设计思路，只留学员看得懂的最短表达。量化口径：**讲解要点≤110字、演示≤80字、学员练习≤80字，单模块四字段合计≤300字**（复杂的核心模块可到350字，但不得靠堆形容词占额度）。同一信息只在一处说清，不把关键词、标题、讲解要点互相复述。修改已有课纲时，这三项的语言量按**压减40%**为默认目标，保留事实、数字、文件名和验收点，删的是修饰与解释。客户版总长保持紧凑，宁可模块内精炼也不堆解释；"更少的概念、更少的工具、更少的技巧，更多的实操、更多的作品、更强的产出"同样适用于课纲文本本身。

## 结构与时间

- Type A（有问卷/调研）：企业背景与定制说明→主讲人→大纲→产出→课件展示→课程现场→课后提供→培训准备。
- Type B（无问卷）：主讲人→本课程说明→大纲→产出→课件展示→课程现场→课后准备→培训准备。本课程说明只含定位、对象、时间。
- 大展宏图保留“业务价值→任务实操→流程复用→验收行动”四段逻辑，不强制固定四个标题或百分比。多日课程先按天区隔，再安排部分及模块。
- 每天有主题和一句课程目标。日标题使用 H3，部分标题 H4，模块可用独立粗体段；不超过 H4。
- 需要总览时按天分别列“时间／课程内容／课堂成果”三列表格，不逐行重复第几天，不把长篇大纲塞进表格。
- 课程说明写天数和每日上下午起止时间。当前办公两天课默认 09:00—12:00、14:00—17:30，用户另有要求则覆盖。
- 相邻教学章节之间安排 15 分钟休息；午休、下课替代额外休息。时间表只写上课时间，空隙体现休息。章内演示、练习、互评不是每段都再休息。
- 起止区间为计算依据，校验重叠、间隔、模块时长及每日收尾；不可照搬标杆原有排期错误。

## AI 与 Agent 核心能力

- **开场模块＝基础认知＋工具导入，不做工具选型块（2026-10-26 用户定）**：以 WorkBuddy 为主线的智能体课/办公课，模块1 固定讲“大模型、Token、上下文窗口、幻觉”，再讲 WorkBuddy 是什么（执行型：读文件、拆步骤、调工具、交可编辑文件）并让学员跑通第一个任务。不把“工具选型”做成独立模块或独立产出物；客户需求原文提到选型时，只在模块1 末尾用一句结论对齐（能交付文件、做法可复用、权限可控、数据留授权范围），不铺四类工具对比。
- 任务交办必须讲清结果、材料、边界、验收，对应 PCR 三要素；区分一次执行、Skill 复用与定时触发。
- 提示词入门统一用 **PCR**（2026-10-25 起替代旧 OC 写法）：**Prompt** 说清要什么成果、按什么做法做；**Context** 给背景、资料与认可样例；**Right** 定清怎么算对——验收标准、核验方式与交付形态。三要素缺一不可，Right 不能省成一句"做好一点"。
- PCR 的 Prompt 讲**“正反合”三招**，客户版写全三招名称：
  - **正向结构化**（正）：按角色、目标、步骤、输出格式正向搭提示词骨架，适合任务清楚、材料现成的场景。
  - **逆向反推法**（反）：从想要的最终结果出发，反推需要交代哪些信息、哪些步骤可以省，先写清终稿长什么样再倒推提示词。
  - **逆向结构化**（合）：拿一份已认可的终稿当样例，倒推它的结构、口径与判断标准，再固化成可复用的提示词；三招配合——正向搭骨架、逆向定内容、样例合口径。
  - 教学顺序按“正视—反推—样例合”走，每一招配一次同任务重做的对比，学员看得见差别再上手机练。
- 旧成稿里出现的 OC 写法按 PCR 理解与改写：OC 的 Outcome 对应 Prompt+Right，Context 对应 Context；改稿时补齐 Right，不保留两套框架名称。
- 上下文实操包括认可样例、业务资料与岗位约束；长期规则和当次材料分开，客户间隔离，过期资料更新。
- 终稿对照与规则沉淀（内部可称Reconcile）：初稿与人工终稿对照→提出改动、可能原因和候选规则→人工确认→保存到合适的规则/记忆入口→换材料复测。客户版优先写“对照终稿，沉淀规则”，不把英文方法名当作产品原生功能；AI推测的修改原因不当成用户事实，不承诺自动写入固定文件。
- 基础权限、安全与幻觉核验是必修，不全部放加餐：独立目录、副本、最小授权、备份、删除/覆盖/外发确认；外部资料中的指令不等于用户授权。
- 降低幻觉：允许未知、区分事实与推测、来源核对、数字重算、真实操作测试。AI 自检不能替代独立证据，不承诺零幻觉。
- 高阶配置、API、复杂连接器、多智能体编排和企业部署按基础与时长分层；本次通用办公两天课放最后一小时加餐。
- 每个大模块案例导入、关键示范、上手、核验修改、保存成果；大 PK 适量，其他环节短互评。产出包括可编辑文件、Skill 或 HTML，不仅截图。
- 学员完成一次可用任务后再封装；重复运行需要触发、输入、异常处理与运行证据。全自动不是所有任务的最终目标。
- 办公/Agent实战优先把作品整合为“岗位AI工作台”：岗位角色、核心Skill、资料入口、偏好规则、任务流程与使用说明。它是成果组织方式，不强制开发新平台；不硬性要求3—5个连接器、10条偏好或多个Skill。其他主题采用适合岗位的成果包。
- PK评价岗位契合度、流程完整度、AI使用与核验、可落地性、团队协作与呈现；不以安装量代替学习效果。一天围绕一个任务做成闭环，两天再增加独立实操深度，不直接压缩课时硬塞全部内容。

## 定制课案例设计（甲方场景驱动）

以下保留 WorkBuddy 端已有定制经验；涉及 D1/D2 的安排适用于两天递进式课程，不覆盖已明确的一天课、工具和客户排期。WorkBuddy 主线课程仍先完成基础导入；“压轴对比”仅适用于先用对话工具再引入 Agent 的课程。

- **案例嵌入模块，不做独立导入段**：每模块=先讲该业务线真实案例（场景引入+方法论）→学员用同类脱敏素材实操；案例是核心不是点缀，原"30分钟案例导入"类设计不采用。
- **"看→用→造"三层递进**：D1看讲师按业务线示范（认知）→D1下午学员用同类脱敏素材实操（体感，豆包/DeepSeek起步）→D2把做过的场景封装成Skill/工作台（落地，WorkBuddy承接）。Day2案例全部承接Day1，不引入新场景；学员两天围绕自己条线的一个场景走完"看懂→做过→封装→立项"。
- **工具对比式教学**：外部Agent工具（如WorkBuddy）压轴出场，用"当天下午做过的同一任务重做一遍"制造对比——学员直接体感智能体与聊天框的差距，比讲功能有效。
- **案例六要素贯穿**：业务问题→AI介入→流程变化→效果→实施条件→可借鉴经验；第一天教拆解，第二天用于路演汇报；效果与实施条件两个要素重点讲，落到需求说明书的"数据与权限"段。
- **多业务线覆盖方式**：实操素材按条线分发（每人练自己条线），产出按条线归组——一个学员两天深耕自己条线，全班全覆盖。
- 需求梳理可引入FDE（前向部署工程师）视角做自检标准："明天FDE进驻你的课题，这份文档够不够他开工"。

## 工具与事实

- 按用户主工具、企业允许范围、账号、设备与网络选型。国产来源不等于自动满足企业合规。
- WorkBuddy课以已验证的原生能力优先。新课程默认不采用、也不在软件适配中列出iSlide与智谱GLM；历史参考里出现的旧工具不构成选型依据。
- 默认一主工具，必要时一个辅助或备用，不把备用工具也安排成全员必学。
- 每个标准产品都写清主工具、兼容/核验工具、账号与环境前提及不承诺范围。课程产品线可分通用能力、平台专项、行业专项与个人经营；直播、录播、线下是交付方式，不能与产品分类混为同一层级。价格未确认前只保留报价结构，不填入销售图。
- 用户指定的原课纲和手册必须实际读取，记录“原有重点→新版模块”的对应关系，不能只用通用参考替代。前沿高管课按“技术前沿→亲手实操→组织研讨”编排；行业课保留指定主工具，再改变材料、场景与产物，不只更换行业名。具体产品要求见references/COURSE-CATALOG.md。
- 官方功能、版本、模型、市场商品和权限属于会变化的信息，正式排课前核对。区分原生能力、模板/扩展实现和未验证设想；不将未经核实的事件触发、免确认安装、自动清理记忆或通用回滚承诺写进课纲。视频和长任务准备备用结果，区分演示、选做与必交。
- 讲师当前确认口径：**2024 年至今已交付超过 200 家头部公司**。其他履历可保留已核实的原表述，不新增背书；好评率、排名、用户数、客户成效未经核实不沿用。
- 课件截图与现场照片仅使用已授权素材；标注历史课件示例，不能宣称新课件已制作完毕。

## 交付

- 输出 Markdown；需要排版时用同一程序生成带图 Word 与固定版式 PDF/预览。
- **标题同步**：H1为唯一标题；客户名仅在文件夹。MD、Word/PDF文件名（`_带图`除外）、Word首页与Title属性必须一致，交付前校验。**MD文件名必须与H1完全一致**（含【】与连字符），排版脚本生成后用 `validate_title_sync.py` 校验，命名不符时先改MD文件名再重跑。
- **定制课培训准备两件套**（客户需要提供数据/场景时写入课纲"培训准备"章节）：
  - **案例数据样例表头表**：按业务线列"案例场景／数据表／表头字段"三列，让客户照表头准备脱敏数据；字段可按实际系统调整。
